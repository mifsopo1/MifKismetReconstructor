# MifKismetReconstructor — audit, 2026-08-31

Audited by pointing MifBridge's static detectors at this plugin's source. Those detectors were
mutation-proven the same day: each was checked by planting a defect it claims to catch and watching
it go red, so a clean result from one of them means something. Where a tool could not see this
module at all, that is recorded as **not checked** rather than as a pass.

The plugin is in good shape structurally — 12 endpoints, 18 `KrRejectUnknownParams` guards, no
blocking calls, no modal-capable API used unguarded. Everything below follows from **one** root
cause, and fixing that root cause closes most of it.

---

## The root cause: MifBridge's public surface is one function wide

`MifKrBridgeEndpoints.cpp:45-48` states the situation exactly:

> MifBridge::RejectUnknownParams and the JStr/JInt/JBool accessors are declared in
> MifBridge/Private/MifBridgeHandlers.h — a PRIVATE header, unreachable from this module even though
> we link MifBridge. The alternatives were (a) reimplement them here or (b) re-export them through
> the new public registry header. (a) is chosen.

That was a reasonable call at the time and it is written down, which is why this audit could start
from it instead of discovering it. But (a) has a running cost, and the cost has now been paid twice.
Everything that makes a MifBridge endpoint *safe* lives behind that private header:
`RejectUnknownParams`, `JBool`'s type strictness, `RecordParamTypeViolation`, and
`MifDeferToNextTick`. A first-class endpoint provider sharing the same HTTP surface either
reimplements them and drifts, or does without and is unguarded. Both happened.

---

## 1. The bool accessors have drifted, and 13 parameters silently ignore valid input

**Severity: high.** Silent, returns `ok:true`, and inconsistent between two endpoint families on the
same port.

`KrJBool` (`MifKrBridgeEndpoints.cpp:182`) is:

```cpp
bool Value = Default;
return In->TryGetBoolField(Field, Value) ? Value : Default;
```

`TryGetBoolField` succeeds **only** for a JSON boolean. MifBridge's `JBool`
(`MifBridgeCommon.cpp`) accepts considerably more, deliberately:

| sent | MifBridge `mif_*` | MifKismetReconstructor `kr_*` |
|---|---|---|
| `true` | true | true |
| `1` / `0` | true / false | **silently the default** |
| `"true"` `"yes"` `"on"` `"1"` | true | **silently the default** |
| `"false"` `"no"` `"off"` `"0"` | false | **silently the default** |
| `"banana"` | default, and `RecordParamTypeViolation` REPORTS it | **silently the default** |

The original carries a comment naming this exact risk — *"Routes through JBool so the spelling-
tolerant form inherits the same type strictness — two implementations of 'what counts as a boolean'
is exactly the drift PM-005 is about"* — and the drift happened anyway, in the copy that comment
could not reach.

`KrJBoolAny`'s own docstring shows the author reasoning about a neighbouring case and stopping one
step short:

> "First present", not "first true": a caller who passes `classify:false` must get false, and a
> value-based fold would silently return the default.

That is right, and `{"classify": false}` does work. `{"classify": "false"}` does not — the field is
present, `TryGetBoolField` fails on it, the loop moves to the next spelling, and the default `true`
comes back with `ok:true`.

**What it costs, concretely.** Thirteen bool parameters, and the defaults make it worse — most are
`true`, so the silent failure direction is "you asked to exclude something and got it anyway":

```
cookedOnly           true     "cookedOnly":"false"  -> still cooked-only
classify             true     a caller cannot turn classification off by string
includeEvents        true     includeRaw           true    includeProperties    true
includeWidgets       true     includeHistogram     true    includePerEvent      true
includeFrameParamMap true     includeOffsets       false   includeBytecode      false
allowAnim            false    verify               false
```

The cross-plugin inconsistency is the part most likely to bite: the same client, on the same port,
gets lenient bool parsing from `mif_*` and strict-silent parsing from `kr_*`. An agent that learned
`"includeRaw": "false"` works will keep using it, and it will keep quietly not working here.

**Fix.** Re-export the accessors through MifBridge's public registry header — option (b) — and delete
the `Kr*` copies. Extracting a shared helper only helps once the copies are gone; leaving both is how
this recurs. If (b) stays undesirable, `KrJBool` must at minimum reproduce `JBool`'s accepted set and
its violation reporting, with a comment on both sides pointing at the other.

## 2. No unattended-script backstop anywhere, and 5 deferred lambdas that would need one

**Severity: medium-high**, and it is the failure mode this bridge treats as worse than a crash — a
modal dialog stops the HTTP server answering while the editor still looks alive.

`GIsRunningUnattendedScript` appears **0 times** in this plugin. MifBridge sets it around handler
work precisely so an engine call that would open a dialog returns its default instead.

Five `SetTimerForNextTick` lambdas would not be covered even if it were set, because a `TGuardValue`
restores on scope exit and deferred work runs after that:

```
MifKrBridgeEndpoints.cpp:2273   SetTimerForNextTick(CreateLambda([Plan](){ ... }))
MifKrBridgeEndpoints.cpp:3513   ... KrSweep...
MifKrBridgeEndpoints.cpp:3642   ... KrSweep...
MifKrBridgeEndpoints.cpp:3764   ... [Plan]
MifKrBridgeEndpoints.cpp:3901   ... [Plan]
```

All five are in the batch/sweep and reconstruct-plan paths — the long-running jobs, where a dialog
would hang the bridge for the longest and be hardest to attribute.

**Fix.** MifBridge already has the answer in `MifDeferToNextTick`, which re-arms the flag *inside*
the lambda — and it is declared in `MifBridgeHandlers.h:413`, the same private header as §1, so this
module cannot call it. The same re-export closes both findings.

## 3. Twelve endpoints, 4186 lines, and no test anywhere

**Severity: high**, because it is what let §1 and §2 stand.

- **0** MifBridge suites reference any `kr_` endpoint.
- KR has **no test files of its own**.

MifBridge has 160 suite files and treats an endpoint without a suite as unfinished. Twelve endpoints
registered into that same surface have never been exercised by anything but hand. `kr_batch_reconstruct`
and the drift/fidelity endpoints mutate assets, which is the category MifBridge covers most heavily
on its own side.

**Fix.** A `test_kr_reconstruct.py` in MifBridge's `tools/` alongside the rest. The bar that matters
first is the refusal contract — every endpoint called with `{}` and with one wrong parameter — which
needs no cooked fixture and would have caught §1 immediately.

---

## 4. MifBridge's static audits structurally cannot see this plugin

Not a defect in this plugin, but it is why none of the above surfaced earlier, and it will hide the
next one too.

Every detector resolves its corpus as `<plugin>/Source/MifBridge/Private` and matches MifBridge's
spellings — `RejectUnknownParams`, `JBool`, `H_<name>` handlers. Pointed at this module they either
find nothing or, worse, report a clean zero from having scanned nothing. This audit worked around it
by mirroring the source into that shape; `audit_loop_writes` correctly refused to report at all
(its known-sites list did not match), and `audit_blocking`'s "0 blocking calls" is **not evidence** —
it found no handlers to scan. The 10 "broken invariants" in `audit_modals` were all `file not found`
for MifBridge sources and are artifacts of the mirroring, not findings here.

**Fix.** Give the detectors a `--source` argument. MifBridge is meant to be a general UE5 tool; its
audits being hard-wired to its own directory is the same private-surface problem one level up.

## What was checked and found clean

Stated because a short findings list is only meaningful next to what it was compared against.

- **Blocking calls** — no unbounded waits. (Weak evidence: see §4.)
- **Modal-capable APIs** — no unguarded `AssetTools`/`ObjectTools` call sites.
- **Parameter rejection** — 18 `KrRejectUnknownParams` across 12 endpoints; the convention is followed.
- **Structure** — the module is layered cleanly (Analysis / AssetGeneration / Toolkit), the engine-fork
  dependency is isolated to a runtime CVar lookup with no compile dependency the other way, and the
  README states the fork requirement before anything else. That last point is unusual and worth keeping.
